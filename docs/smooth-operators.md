# Smooth Operators: build handoff

The live 21-day cohort app at `omibell.com/smoothoperators`. This document covers
what was built, how to set it up, how to test it, and what the owner still has to
supply before it can sell or release content.

Nothing here has been deployed, no cards have been charged, and no messages have
been sent. Email delivery defaults to `off`, and live checkout stays disabled
until every launch requirement is met.

## Enrollment flow: pay first, fit check, review

1. **Sign in** with an email code.
2. **Fit check** (required before payment; private to admins). It asks for:
   - first and last name, phone
   - business name, website (or "no website yet")
   - full address (US state + ZIP, or outside the US)
   - stage of business, revenue so far, years in business
   - prior operations work (yes/no), full-time staff (yes/no), team size (staff + contractors)
   - one open question: most pressing operations questions

   Everything except the names, contact details and the open question is a single tap. Early-stage answers (idea stage, or under $10K revenue) show a gentle note, never a block. The member must tick that they understand the review and refund policy.
3. **Payment** through Stripe Checkout.
4. **Review** in admin → Members. Each paid member is "pending review" until Omi chooses one of:
   - **Approve:** the enrollment becomes non-refundable, and an approval email goes out (if email sending is on).
   - **Not a fit:** a full refund is issued through Stripe, and access ends. Their saved writing is kept.

   Approved enrollments can't be refunded from the review screen.

**Hidden seat limit:** default 30, set in Cohort settings and never shown publicly. Seats count active enrollments that aren't "not a fit", plus other people's unexpired checkouts. When none are left, the landing page and checkout just say "All seats are full." If two people pay for the last seat at the same moment, both get in, and the purchase is flagged `over_capacity` for review.

**Admin entry:** log in at `/admin`, then choose **Blog admin** or **Smooth Operators admin**. The Smooth Operators admin links back with "← Omi Bell admin". The **Members** tab shows every fit-check answer, filters by review state, lists fit checks without payment (for follow-up), and exports a spreadsheet (CSV).

## Key design decisions

- **Identity:** Supabase Auth email one-time codes (or the emailed link). There are no passwords, so recovery is the same as sign-in on any device. Members sign in *before* paying, so every purchase belongs to a verified user ID. A purchase can never be claimed by typing an email.
- **Payments:** Stripe-hosted Checkout through the REST API, with the webhook signature verified by hand (no SDK). The price is chosen by server time: $999 (99900 cents) before the cutoff, then $1,497 (149700). Client-sent amounts are ignored.
  - At most one in-flight purchase per member, enforced by a unique index. Stripe idempotency keys stop duplicate sessions.
  - Access is granted **only** when Stripe confirms a paid session, either through the signed webhook or a server-to-server lookup when someone returns before the webhook arrives. The success URL alone grants nothing.
- **Intro-price policy:** a session quoted before the cutoff keeps its price until its own Stripe expiry (`checkout_ttl_minutes`, default 60, range 30–1440). After that, new sessions are quoted at the regular price and the stale session is expired at Stripe. Open sessions are never silently repriced.
- **Refunds and disputes:** a full refund suspends access by default (configurable). A dispute keeps access and flags the purchase for review (configurable). A won dispute restores access. Journals and progress are never deleted.
- **Test-mode safety:** test payments create enrollments flagged `is_test`. Test checkout is refused on the production deployment unless `SO_ALLOW_TEST_CHECKOUT=true`. Webhook events from the other Stripe mode are ignored.
- **Schedule:** timestamps are stored in UTC, and scheduling uses the cohort's IANA timezone. Day N unlocks at `unlock_time` on `start_date + N − 1` in cohort time. Members see a day only when it is **unlocked by time and published**. Locked days send only an approved preview title/summary and the unlock date.
- **Journal:** one row per user + cohort + day, with revision-checked saves (a stale tab gets a conflict, never a silent overwrite). Each entry keeps the question it answered when the admin edits the prompt. Autosave keeps a local backup of unsent text. Admin views never include journal text.
- **Data access:** the server connects with `SO_DATABASE_URL`. Every table has RLS enabled with no policies, and `anon`/`authenticated` are revoked, so the public Supabase REST API can't read any of it. All authorization happens on the server.

## Setup

1. **Database:** in the Supabase SQL editor, run `supabase/smooth_operators.sql`, then `supabase/smooth_operators_seed.sql`. Both are safe to re-run. The migration also creates the private `smooth-operators` storage bucket.
2. **Supabase Auth:**
   - Enable Email sign-in.
   - Add `https://www.omibell.com/smoothoperators/login` to Redirect URLs.
   - Edit the "Magic Link" email template to include the code (`{{ .Token }}`) as well as the link.
   - Configure custom SMTP (the built-in sender is heavily rate-limited).
3. **Stripe (test mode first):**
   - Create a webhook endpoint at `https://<domain>/api/smoothoperators-webhook` for these events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, `charge.dispute.created`, `charge.dispute.closed`.
   - Turn on "Email customers for successful payments" so Stripe sends receipts.
4. **Environment variables:** see `.env.smoothoperators.example`. The new ones are `SO_DATABASE_URL`, `SUPABASE_ANON_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET` and `SO_SITE_URL`, plus the optional `SO_*` and `STRIPE_*` settings.
5. **Admin:** go to `/smoothoperators/admin` and log in with the existing site admin password. To use a Supabase account as admin instead, sign in once, then run `update so_profiles set role = 'admin' where email = '…';` in SQL. That role can't be set from the app.
6. **Deploy:** push to the Vercel project as usual. Use a preview deployment with test keys first.

## Running locally and testing

```bash
npm install
npm run so:db                                      # throwaway Postgres 16 on :54329
npm run so:test                                    # unit + integration
PW_CHROMIUM_PATH=/path/to/chromium npm run so:e2e  # browser e2e (path optional)
```

The integration and e2e tests boot a fresh database from the real migration and seed, then run the real dev server. They use local **test doubles** for Supabase Auth, Supabase Storage and Stripe (`tests-so/support/mock-services.js`). The double signs webhooks with Stripe's algorithm, so the app's real signature check is what gets exercised. `STRIPE_API_BASE` is ignored on production deployments.

### Verified results (this build)

- **Unit tests: 8 passing.** Covers DST gaps and overlaps, the year change, viewers in other timezones, cutoff boundaries, quote expiry and access policy.
- **Payment integration tests: 16 passing.**
  - Landing copy and price before and after the cutoff.
  - Auth is required; tampered amounts are ignored; concurrent clicks share one session.
  - The intro quote is honoured until expiry, then the next session is regular price.
  - Success URL alone, cancel, forged webhooks, failed async payments: none grant access.
  - Duplicate and repeated webhooks enroll exactly once; a delayed webhook is reconciled.
  - A session can't be claimed from another account.
  - Refunds suspend access but keep the journal; disputes are handled.
  - Live mode stays blocked until ready; test checkout is refused on production.
- **Member integration tests: 16 passing.**
  - Every lifecycle state.
  - Isolation between cohorts for introductions; moderation.
  - Draft and locked content never leaks (calendar, day, API).
  - Today and the day page return the identical record.
  - Journal conflicts and racing first saves; prompt versioning; journal privacy across members and admin views.
  - Admin role enforcement.
  - Library dedupe across days; file gates; practice transcripts and playback.
  - Calls: join window, `.ics` in UTC, replay publication, private challenges.
  - Admin preview writes nothing; schedule impact preview, re-confirmation and audit log.
  - Post-cohort access policy; input validation.
- **Playwright e2e: 8 passing (desktop and mobile Chromium), with axe WCAG 2 A/AA checks.**
  - Landing → sign in → test-double checkout → verified enrollment → welcome countdown → Day 1 → autosaved reflection survives reload → completion shows in calendar and journal → landing shows "Open My Cohort".
  - Mobile drawer: Esc closes it and returns focus.
  - Signed-out and non-member gates.
  - Admin: publish gate, impact preview, lifecycle preview.

**Not verified here:** real Supabase Auth email delivery, real Stripe test-mode sessions and webhooks, Supabase Storage uploads, and Vercel's own routing. These need the provider credentials. Test them on a preview deployment using the checklist below. Safari and Firefox were not run.

## Owner launch checklist

The admin **Overview** shows these live. Checkout stays off until every "blocks live sales" item is done.

### Blocks live sales
Default cohort dates are **January 4–24, 2027** (Week 1 Jan 4–10, Week 2 Jan 11–17, Week 3 Jan 18–24). If the seed was already run with an earlier start date, change Day 1 in admin Cohort settings (or run `update so_cohorts set start_date = '2027-01-04' where slug = '2027-01';`).

- [ ] Stripe **live** secret key and live webhook signing secret. Optionally, live Price IDs.
- [ ] Tax treatment decided (Stripe Tax on or off), and a "Tax treatment statement" published.
- [ ] Cohort settings confirmed by Omi in admin. This means "Save and confirm as owner" on these values:
  - Price cutoff time and timezone (default: 12:00 a.m. Dec 1, 2026, Pacific)
  - When introductions open
  - Daily unlock time
  - Enrollment closing date and late-entry behaviour
  - Checkout expiry
- [ ] Post-cohort access policy chosen (until a date, or no end date), and an "Access duration statement" published.
- [ ] Publish the refund policy. Omi's wording is pre-filled: refund in full if not a fit; non-refundable once approved. Have it reviewed, then click Publish. Also publish the terms, privacy policy, and call recording and replay policy.
- [ ] Decide how quickly fit checks are reviewed (for example, within 3 business days, and always before January 4), and add that to the refund policy text.
- [ ] Support contact email (and optional response expectations) published.
- [ ] At least one Solutions Seat call scheduled with a confirmed date.
- [ ] Live transactional email: a verified Resend sender domain, `SO_EMAIL_DELIVERY=live`, and the Supabase Auth SMTP and template configured.
- [ ] "Sales switched on" in Cohort settings.

### Blocks cohort content release (each day)
- [ ] Final lesson, reflection and action reviewed. Untick "sample", tick "reviewed and final", then publish.
- [ ] Preview title and summary approved for the calendar.
- [ ] Guided practice audio uploaded with duration and transcript, then published.
- [ ] Toolkit templates uploaded or linked with approved usage terms, tagged by pillar, linked to days, then published.

### Landing page and brand
- [ ] Approved logo, palette (the current palette is exploratory), Omi photo, credentials and verified examples.
- [ ] A specific time commitment (only once confirmed).
- [ ] FAQ answers approved and published. Five are drafted from facts in the brief; four are left blank on purpose: recordings, access, refunds, legal review.

### Not built in this version (by design or pending decisions)
- Reminder emails: the preferences are stored, but nothing sends them.
- Compiled playbook export (not promised anywhere).
- Server-side journal search.
